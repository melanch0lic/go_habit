# Профили, никнеймы, друзья и блокировки

## Идентичность

- Каноническая идентичность — `auth.users.id`. Никнейм — изменяемое отображаемое имя, нигде не используется как
  внешний ключ.
- Другие пользователи видят только `profile.public_id` — случайный непрозрачный идентификатор (неизменяем, триггер
  `profile_keep_public_id`). Auth-id, email, привычки и история отметок наружу не отдаются.

## Никнейм

- Формат: 3–20 символов, латинские буквы, цифры и `_`, первая — буква (`^[A-Za-z][A-Za-z0-9_]{2,19}$`).
  Зарезервированные имена (`admin`, `support`, …) запрещены. Регистр сохраняется для отображения.
- Уникальность без учёта регистра — уникальный индекс `profile_nickname_key` на `lower(nickname)`. Одновременные
  попытки занять один никнейм: одна проходит, вторая получает `23505` → «Этот никнейм уже занят».
- Проверка при вводе: `nickname_status()` с debounce 400 мс; устаревшие проверки отменяются. Окончательное решение —
  только у базы при сохранении.
- Пользователи без никнейма (новые и существующие аккаунты) после входа видят экран «Выберите никнейм» один раз за
  запуск; его можно отложить, трекинг привычек от него не зависит.
- Аватар: один из 12 пресетов (ключ в `profile.avatar`) или по умолчанию пиксельный узор из никнейма. Хранилища
  изображений в проекте нет, поэтому загрузка фото не добавлялась.

## Дружба

- Таблица `friendship`: одна строка на неупорядоченную пару (`user_low < user_high` — первичный ключ). `pending` —
  заявка от `requester_id`, `accepted` — дружба. Обратная дублирующая заявка физически невозможна.
- Отклонение, отмена, удаление и блокировка удаляют строку — пара может начать заново.
- Встречные заявки: если B отправляет заявку A, когда A уже отправил заявку B, она принимается (дружба), а не
  создаётся вторая. Гонка двух одновременных заявок разрешается так же (`on conflict` + `for update`).
- Принять/отклонить может только получатель, отменить — только отправитель; проверки — в функциях на сервере.
- Все действия идемпотентны и возвращают итоговое отношение; повтор запроса не создаёт дублей.

## Блокировка

- `user_block (blocker_id, blocked_id)`. Блокировка удаляет дружбу и любые заявки между пользователями.
- Заблокированный не может найти блокирующего, открыть его профиль или отправить заявку — для него это выглядит
  как «пользователь не найден» (тот же `P0002`, что и для несуществующего). О блокировке он не узнаёт.
- Заблокировавший видит пользователя в разделе «Заблокированные» и может разблокировать; отправить ему заявку можно
  только после разблокировки (`P0004`).

## Приватность

- Всем, кто нашёл пользователя: никнейм, аватар, описание.
- `stats_visibility` (по умолчанию «Только друзья»): активные привычки, регулярность за неделю, число друзей, а также
  никнейм в рейтингах сообществ (иначе — «Участник»). «Никто» исключает и из рейтинга друзей.
- `communities_visibility` (по умолчанию «Только друзья»): другие видят только общие с ними сообщества.
- Никогда не показываются: email, заметки, названия привычек, история отметок.

## Рейтинг друзей

`friends_leaderboard(p_today)`: пользователь и его друзья (кроме скрывших статистику), правило
`weekly_consistency_v1` по всем активным привычкам — как в сообществах: неделя с понедельника по сегодня, по каждой
привычке засчитываются дни с max(начало недели, день создания) по сегодня, будущие дни не считаются; процент =
выполненные / засчитываемые. Порядок: процент ↓, выполненные дни ↓, никнейм. Счёт считает только сервер.

## Уведомления

Отдельной системы уведомлений в проекте нет (экран уведомлений — макет). Социальные события берутся из самих
заявок, поэтому дублей быть не может: бейдж с числом входящих заявок на кнопке профиля и в разделе «Друзья», а во
вкладке «Заявки» — «@nick принял(а) вашу заявку» за последние 7 дней.

## Клиент и офлайн

- `lib/feature/social/`: модели, `SocialRepository` (Supabase RPC + кэш в Drift), BLoC-и (`MyProfileBloc`,
  `FriendsBloc` — над навигацией; `ProfileEditBloc`, `PublicProfileBloc`, `FriendsLeaderboardBloc` — на экранах).
- Экраны: свой профиль (раздел на вкладке «Профиль»), «Друзья» (вкладки «Друзья», «Заявки», «Рейтинг»),
  публичный профиль `/users/<public_id>`, редактирование профиля, «Конфиденциальность».
- Drift v6: `social_cache` — подтверждённые сервером профиль и список друзей для офлайн-просмотра; очищается при
  выходе. Действия требуют сети и не ставятся в очередь: интерфейс не показывает заявку отправленной или принятой,
  пока сервер это не подтвердил.

## Безопасность

- `friendship` и `user_block` клиентам недоступны совсем (RLS включён, прав нет): все чтения и записи — через
  `security definer` функции с `search_path = ''`, проверкой `auth.uid()` и правами только для `authenticated`.
- Внутренние функции (`_are_friends`, `_can_see`, `_weekly_totals`, …) клиентам не выдаются.
- Свой профиль: RLS «только своя строка»; колоночные права на `nickname, bio, avatar, stats_visibility,
  communities_visibility`.
- Проверки: `supabase/tests/database/03_social.test.sql` (55 pgTAP-проверок, включая сквозной сценарий A/B).

## Дальше

Структура готова для вызовов, командных целей, реакций и уведомлений: отношения и видимость централизованы в
`_relationship` / `_can_see`, а клиент получает события через `SocialRepository.changes`. Приглашения в сообщества
не добавлялись: сообщества открыты, модели приглашений нет.
